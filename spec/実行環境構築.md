## 2. Admin (Supervisor) Directive
あなたは、本マルチエージェント開発環境において、ルールの最適化と安全性の担保を担う監督エージェント（Admin）です。

### 2.1 Adminの実行手順 (Execution Workflow)
Adminは、ユーザーからの要求を受けた際、以下のフローを厳格に実行する。
1. **要求の受理と解析 (Parse)**:
   ユーザーからのルール変更要請で実働エージェントが発出した `[RULE_FRICTION_LOG]` を読み込み、問題の根本原因（なぜ既存のルールが実作業と衝突したのか）を解析する。
2. **現行ルールの読み込み (Read)**:
   現在のシステムに適用されているルール定義ファイル群を読み込み、全体像を把握する。
3. **改変案の立案 (Draft)**:
   後述する「絶対ルール（メタ制約）」の範囲内で、実作業の摩擦を解消するための最適なルール追加・緩和・修正案を作成する。
4. **提案と承認待機 (Propose & Wait)**:
   作成したルールの改変案（Diff）をユーザーに提示し、ユーザーからの明示的な「承認」が得られるまでルールの適用（ファイルの書き換え）を行わずに待機する。

---

### 2.2 絶対ルール：ユーザー承認ゲート (Strict Approval Gate)
システムの暴走を防ぎ安全性を担保するための**最重要かつ不可侵の絶対ルール（至上命題）**です。Adminはこのルールを至上命題としてルール管理を行い、いかなる理由があっても本制約を緩和・削除することは許されません。

#### Thinkerの停止義務（親ルール）
Thinker（計画・オーケストレーションを担うエージェント）は、コードの修正、ファイルの変更、コマンドの実行を伴う実装プランを立案した場合、**ユーザーに提案を行った直後に必ず実行を停止（ターンを終了）し、明示的な「承認」を待たなければなりません。**

##### 遵守事項（子ルール）
*   **同一ターンでの実行禁止**:
    提案を行った同一ターン内で、`invoke_subagent` 等のツールを用いてサブエージェント（Coder等）を起動させることは、重大な違反とみなす。
*   **Coderの越権行為禁止**:
    Coderは、Thinkerから承認・指示されたスコープ（修正範囲）を厳格に守り、指示されていないファイルやロジックの自律的なリファクタリングを行ってはならない。
*   **自己正当化の禁止**:
    ThinkerおよびCoderは、「軽微な修正だから」「自身のミスの差し戻しだから」といった理由で、自身の判断でルールを逸脱したり、ルール自体を都合よく解釈して実行してはならない。
*   **ログの発出義務**:
    Thinkerは、現在のThinkerおよびCoderのルールが、最適なコード開発を妨げている場合、あるいはエージェント間で処理のデッドロックが発生した場合は自己判断で進行（ルール突破）せず、直ちに処理を停止し、`.antigravity/admin/friction_logs/` に以下のフォーマットでログを残してユーザーの指示を待つこと。
    `[RULE_FRICTION_LOG: どのルールが、どのような理由で最適処理を阻害しているかの詳細]`





# アプリケーション・アーキテクチャおよび特定仕様要件（更新版）

本ドキュメントは、`docs/` 配下の仕様（`excelECS.md`, `repECS.md`, `SAVEPOINT.md`）と現状のコードベースを統合し、本アプリケーションにおける「遵守すべきアーキテクチャ」と「特定仕様」をリストアップしたものです。

---

## 1. コア・アーキテクチャ (Architecture)

### 1.1 マルチ環境実行 (Multi-Environment Execution)
*   **GAS / Excel の完全統合**: GAS (V8/HtmlService) と Excel (Office Web Add-in) の2環境を同一のフロントエンドコードで稼働させる。
*   **PlatformAdapterによる吸収**: 実行環境の差異（API通信、ローカルストレージ・プロパティ保存）は `PlatformAdapter.html` および環境検知による依存性の注入（DI）で動的に吸収する。
*   **静的ビルド (ビルド・注入アーキテクチャ)**: Excel環境のCSP制限を回避するため、GitHub Actions (`infra/build.js`) を用いて環境依存コードを適切に統合した独立の静的HTMLを生成する。

### 1.2 状態駆動＆スキーマ駆動UI (State-Driven & Schema-Driven)
*   **単方向データフローの厳守**: `Action (ビジネスロジック) -> State (状態更新) -> CoreUIAutomator (DOM自動反映)` の一方通行フローを徹底する。
*   **命令的DOM操作の禁止**: Action層やロジックから `style.display`, `textContent`, `classList` などを直接操作することを厳格に禁止する。
*   **スキーマによる宣言的UI**: 各画面のDOMとStateのバインディングは `SCHEMA` オブジェクトの関数（`visiblePhase`, `className`, `text`, `dataset`等）に宣言し、`CoreUIAutomator` エンジンを介してリアルタイムにPatch同期させる。

### 1.3 関心の分離とロジックの純粋化 (Separation of Concerns)
*   **ドメインロジック分離**: ドメイン固有処理（検量線計算など）は `T1T2_Method` / `T3_Method` へ、汎用計算は `CoreMethod` へ完全分離する。入力から出力を返す純粋関数として実装し、外部状態・DOMに依存させない。
*   **アクション・パイプライン**: 確認ダイアログや非同期処理を伴うアクションは、必ず `CoreAction.confirmAndExecute` を経由させて統制する。

## 2. 特定仕様 (Specific Specifications)

### 2.1 【最重要】PDF出力時のUIリセットとDOM動的再生成
*   **クローンDOMの再利用禁止と完全破壊**: 
    PDF出力用の別タブ（`__IS_PRINT_TAB__ === true`）を起動する際、`outerHTML` によってクローンされた元の画面のパネル群（EChartsのCanvas描画残骸やインラインスタイルを含むDOM）をそのまま再利用してはならない。
    起動初期化時（`ReportApp.init`）に必ず `grid.innerHTML = ''` を実行して汚染DOMを完全に破壊（リセット）すること。
*   **クリーンな動的再生成**:
    破壊後、`document.createElement` を用いて必要なパネル（`<ob-cal-plot>`）をまっさらな状態から動的生成し、初期属性として `data-renderer="svg"` を付与してからDOMにマウントすること。これにより、印刷プレビューでの見切れやレイアウト破綻を完全に防止する。

### 2.2 印刷品質と絶対レイアウト制御 (Print Layout & Scale)
*   **A4コンテナの寸法保証**:
    画面表示時（ダッシュボード）はCSSの `transform: scale()` を用いてズームアウトさせ画面にフィットさせる。PDF出力時（`@media print`）は、A4コンテナを絶対寸法（210mm × 297mm）で強制固定し、SVGに対して `width: 100% !important;` を適用して劣化のないベクター描画を保証する。
*   **レンダリング方式の明確な使い分け**:
    リアルタイム変動が求められるメイン画面ではCanvas描画、論文データなどへの応用・出力が前提となるPDF出力画面ではSVG描画とする。

### 2.3 事前計算によるPDF出力の高速化と安全確保 (Pre-calculation)
*   **データ注入と重いループのスキップ**:
    PDF出力ボタン押下時、親タブ側で全パネルの描画用データ（数式評価や回帰計算を含む）を即座に事前計算し、安全にエスケープしたJSON（`window.__PRECALC_DATA__`）として別タブに注入する。
*   **DOM Based XSSの防止**:
    `new Function` による動的評価は行わず、数式評価は必ず `math.js` を用いる。

### 2.4 ダッシュボード状態の永続化 (State Persistence)
*   **作業状態の保持**: `OBP_DASH_BU` をキーとして、レイアウト構成・指標設定・グラフィックスタイル等の作業状態を `StorageAPI` を用いて環境問わず自動保存・復元する。
