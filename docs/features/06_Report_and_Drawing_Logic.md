# 06_Report_and_Drawing_Logic.md

## 1. Report層のアーキテクチャとデータ構造
Report層 (`Report.html`, `Report_APP.html`, `Report_Logic.html`, `Chart.html`) は、本体アプリケーション（Sidebar）から完全に独立して稼働する単一のHTML（SPA）のレンダリングエンジンです。
* **静的結合とデータ注入:** 実行時の動的評価は行わず、コアロジックは静的結合されます。Dash層から生データ（`__INJECTED_DATA__`）とお気に入り設定（`__INJECTED_FAVORITE__`）が文字列として注入され、独立したコンテキストで動作します。
* **グラフパネルの静的定義と動的バインディング:**
  `Report.html` 側では `<div class="dash-grid">` 内に最大数である9個の `<ui-plot>` カスタム要素を静的に事前マウントしています（`p_0`～`p_8`）。State（`RPTST`）の行・列数の変更に応じて、必要なパネルだけをCSSレイアウトで可視化し、アクティブパネル（`$active`）のプロパティをサイドバーのインスペクタUIへ動的にバインドするアプローチをとっています。

## 2. 特殊なUI設計と精密レイアウト制御
* **SIDEFIXとズーム耐性の分担:**
  画面左側の固定サイドバーは、OSやブラウザがズーム（`devicePixelRatio`）されてもサイドバー自体の物理的なピクセルサイズ（見た目の大きさ）を一定に保つよう、`SIDEFIX` クラスによって自律制御されています。一方、右側のA4コンテナは「プレビュー画面兼、印刷レイアウト画面」としての役割を持つため、あえて拡縮を許容し、全体像の確認ができる設計になっています。
* **UIPlotによるリサイズ監視:**
  描画コンポーネントである `<ui-plot>` は内部に `ResizeObserver` を持ち、ズームや枠の変更等でコンテナの物理サイズが変化した時にのみ自律的に再計算と `echarts.resize()` を発火させるライフサイクルを持ちます。
* **出力時の再構築とSVG/Canvas使い分け:** 
  メインのUI画面では軽量な Canvas を使用しUXを最大化します。PDF出力（印刷用iframeへの注入）や静的HTMLの起動時は、DOMを再利用せず `innerHTML = ''` で完全破壊し、明示的に `data-param="svg"` をセットして劣化のないベクターデータとして再構築します。

## 3. Report内でのUI単位変換 (UI Unit Conversion)
ユーザーがサイドバーのインスペクタで入力する値は、内部で厳密な単位変換を経て描画エンジンに渡されます。
* `ReportMethod.buildGraphStyle` が翻訳層として機能し、ユーザーが指定した `pt`（フォントや線幅）は `1.33` 倍してピクセル（`px`）に、`mm`（余白など）は `3.78` 倍してピクセルに変換します。
* また、色指定における `K%`（墨アミ）は HSL 形式（`hsl(0, 0%, 100-K%)`）に変換され、EChartsが直接解釈できる絶対的なスタイルオブジェクトとして一元化されます。これにより、A4用紙サイズという物理寸法と、ブラウザの描画ピクセル間のズレを吸収しています。

## 4. スケールと目盛の自動算出・同期処理
グラフのX/Y軸の目盛（スケール）は、`ReportMethod.calculateBaseScales` によって自律的に事前計算されます。
* **Auto（自動）とManual（固定）の算出範囲の違い**:
  ユーザーが「Auto」を選択した場合、現在適用されているすべてのフィルター（Database, Item, Group）を通したデータ群の最小・最大値を見てスケールがズームされます。一方「Manual」を選択した場合、Item/Groupフィルターを無視し、Databaseフィルターのみを通した「全体データ」の最小・最大値を基準にスケールが固定されます。
* **カスタム単位の再構築**:
  UIから生成された選択肢を用いてユーザーが目盛単位（Tick）を固定した場合、`ReportMethod._makeCustomScale` が呼び出され、EChartsの自動計算を上書きして「指定単位に基づいた美しい最小値・最大値」を強制的に再計算します。

## 5. プロット領域計算ロジックとモード別分岐
グラフの描画領域（プロット幅 `plotW`・高さ `plotH`）は、モードによって `ChartRenderer.buildOption` に渡される計算ロジックが分岐します。
* **検量線（calib）**: 傾き（回帰）を視覚的かつ分析的に正確に評価（1:1で評価）するというビジネス要件から、`ReportMethod.calculatePanelMetrics` を通じてプロットエリアは縦横比1:1の正方形（`square`）に強制ハードコードされます。
* **判別図（clus）**: ユーザー指定の行アスペクト比（`rowAspect`）に基づく `custom` モードとして計算され、`ReportMethod.calculatePanelMetricsAspect` によってコンテナの縦横の制約内で最大限描画できる領域が数学的に計算されます。
* **安全マージンの自律制御**:
  EChartsの自動レイアウトに依存せず、事前にフォントサイズやタイトル有無から必要な余白を `ChartRenderer.getGridMargins` で厳密に計算し、外枠の絶対ピクセル数を強制生成することでラベルの見切れを完全に防止しています。

## 6. モード別グラフデータ準備（動的補正と数式評価）
`ReportMethod.buildChartConfig` がマスター組み立て関数として機能し、`CHARTDT.genChartDB` を呼び出して描画直前にオンザフライでデータを計算・結合します。
WDXRF（基準値）とPXRF（計測値）を試料IDで結合し、LOD置換や検量線補正（`useCal` トグルがONなら適用）を行います。
* **検量線モード**: 結合データから回帰直線（傾きと切片）を動的に算出し、統計情報（R²など）を生成します。
* **判別図モード**: ユーザーが入力した「(Fe+Ti)/Mn」のような任意の数式を `math.js` エンジンで評価し、X/Y座標へマッピングします。この際、**検量線適用トグルがONであれば、数式評価の元データとして「補正済みのPXRFデータ」が正しく波及・使用される仕様**になっています。

## 7. エクスポート機能の業務的使い分け
Report層（`RepoExport` および `ReportMethod.generateExportHTML`）の出力機能は、用途に応じて使い分けられます。
* **お気に入り（設定保存）**: ダッシュボード側のスプレッドシート（またはExcelファイル）固有のプロパティとして保存されます。ユーザーが元データを差し替えても、同じレイアウトや設定を再利用するための「作業者固有の永続化」役割を持ちます。
* **HTMLアプリ**: データ注入後のReport層自体をスタンドアロンなHTMLとして出力します。元データを持たない他部署のユーザー等へ共有し、受け取った側が表示切替や見た目変更を自由に行える「インスタンスアプリ」としての役割を持ちます。
* **PDF**: ブラウザ印刷機能を利用し、A4絶対寸法のベクターPDFとして出力します（非同期データ計算による白紙化を防ぐため、事前に全データを計算してから印刷を発火させる安全機構を持ちます）。

## 8. Report特有のライフサイクル・リアクティブ (`RepoReact`)
Report層では、DOMを直接書き換える手続き型の処理を排し、`State.subscribe` でプロパティの変化を監視してUIやグラフを更新するリアクティブ設計を採用しています。
スライダーのドラッグや設定の連続変更などが発生した際、描画処理（`RepoRend.syncPanelDom` や `genCharts`）に 250ms のデバウンス（遅延実行）をかけることで、重い再計算によるフリーズを防ぎ、滑らかなUXを提供しています。
