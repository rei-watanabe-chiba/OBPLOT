# 05_trace5i_Logic.md

## 1. Tracer5i層のアーキテクチャと目的
Tracer5i層は、機器から出力されるRAWデータの読み込み・整形から、分析（検量線作成）用データの準備、および基準値との照合までの一連のフローを担う。
従来の2タブ構成（`entry` / `adapter`）および `ADPST` / `ADPAct` は廃止され、単一画面・単一ステートツリー（`ENTST` / `ENTAct`）による直列ワークフローに統合された。
スプレッドシートメニューも「tracer5i抽出（`openSidebarENT`）」に一本化され、起動時の環境検証スキーマ（`GLB.schema.ent`）によって全関連シート（`ファイルリスト`, `File`, `Results`, `tracer5i`, `WDXRF`, `検量線`, `PXRF`）が一括で検証される。

## 2. データ抽出フェーズ (ENT: Entry)
計測機器からのRAWデータを取り込み、データベースとして蓄積可能な一次データプール（`tracer5i`シート）を構築するフェーズ。

* **データソースの役割**:
  * `File` シート: ユーザーが手入力するメタデータ。計測ファイル番号、モード、資料ID、任意でsub_id（同一資料の複数回計測を区別）や備考（info）が定義される。
  * `Results` シート: 計測機器から出力されたRAWデータ。`File`のファイル番号と紐づく。一つのデータ内に異なるモードの計測結果が混在しており、ヘッダー構成も複数存在するため、あらかじめ定義された `obsidianIndex` や `mudrockIndex` を用いて抽出を行う。
* **モード別の抽出検証ロジック (`Single` / `Dual`)**:
  * `Dual` モード: 1つの資料に対し、照射面を変えずに連続して2つの計測モード（Obsidian/Mudrock）を実行した場合のデータを抽出する。同一計測ID（`scanId` = 資料ID + sub_id）に対して、必ず2行（両モード）が存在しなければエラーとする。
  * `Single` モード: 目的の元素が限定されており、単独照射で取得されたデータを抽出する。バリデーションが緩く、同一計測IDに対して複数行存在する場合のみエラーとする。
* **データ抽出と変換 (`genExtr`)**:
  * 抽出の際、数値データには `%` から `ppm` への単位変換として `* 10000` が適用される。
  * また、機器固有の誤差データとして、測定値の右隣の列の値を必ず誤差（`_Err`）として取得する。
  * UIで指定された抽出設定（`database`, `item`, `date`）は、1回の抽出バッチ共通のメタデータとして全ての抽出行に付加される。
* **`tracer5i` シートへの格納と重複排除 (`valdPxrf`)**:
  * `tracer5i` シートは、過去の抽出結果もすべて蓄積していく一次データ（RAWデータ）のマスタープールである。
  * 以前の中間シート（「抽出データ」シート）および2段階保存（`pushExtr`）は廃止され、「データを抽出」実行時（`ENTAct.runExtr`）に `ファイルリスト` の検証・`Results` からのデータ抽出（`genExtr`）・`tracer5i` シートとの重複判定（`valdPxrf`）を一括で実行するフローに統合された。
  * 重複判定の結果に応じて確認ダイアログを表示し、重複時は既存の古い行を置換して全体上書き、非重複時は末尾追記として直接 `tracer5i` シートへ書き出し（`API.pushMult`）を行う。
  * 格納完了（`OUTPUT` フェーズ到達）後に続けて別バッチを連続抽出する際、`database` 入力欄の編集時（`ENTAct.valdExtrRefs`）にフェーズを `VALID` に戻すことで、アコーディオン（`secEXTR`）が閉じずに連続して抽出作業を行える。

## 3. 検量線・標準化フェーズ
蓄積されたPXRFデータと、正解値であるWDXRFデータを照合し、補正モデルの算出および後段（Report層）へ渡すためのデータ構造の標準化を行うフェーズ。

* **データベースの初期化と「更新時読込」方式 (`initDB` / `syncTrcDB`)**:
  * 旧来の手動「データ読込」ボタン（`loadDB`）は廃止された。
  * アプリ起動時（`TrcInit.start` の `onBeforeInit` フックで呼び出される `ENTAct.initDB`）に、`tracer5i`・`WDXRF`・`検量線`（旧 `Correction` シート、`GLB.appShts.crct = "検量線"`）の各シートをバックグラウンドで初期読込する。
  * 以降、`tracer5i` データは「データを抽出（`ENTAct.runExtr`）」完了時に `ENTAct.syncTrcDB` で即時更新され、`検量線` データは「検量線出力（`ENTAct.pushCrct`）」完了時にState更新される「更新時読込」方式により、常に最新のシート状態が同期される。
* **直列フェーズ遷移とUIアンロックフロー**:
  * 「抽出と格納（`secEXTR`）」が完了して `OUTPUT` フェーズに到達すると、「データセット選択（`secASGN`）」セクションがアンロックされる。
  * フィルタ条件を選択して「データを確定（`ENTAct.fltrDB`）」を押下すると、フェーズが `FILTERED` に進み、「プレビュー（`secPREV`）」と「出力と標準化（`secSTDZ`）」の2つのセクションが同時にアンロックされる。
* **シンボル設定（`secSYMB`）の統合**:
  * 従来の独立した「シンボル確定」ボタンは廃止された。
  * シンボル設定は「プレビュー（`secPREV`）」内の末尾に、「プレビュー補正設定（`secCALB`）」と並列のサブセクション（`details.sub-sec`）として配置される。
  * 軸変更（`valdAxis`）やルールの追加・編集・削除を行うとStateが即時更新され、「プレビュー更新（`ENTAct.genPrev`）」実行時に現在のシンボル設定がそのままグラフへ反映される。
* **データの照合**:
  * `tracer5i` シートの計測値（PXRFデータ）と、`WDXRF` シートの真値（正解・基準値）を結合する。
  * 照合キーには `database` + `ID (資料ID)` を用いる（WDXRFは計測回数ごとの `sub_id` を持たないため）。
* **元素抽出モードのフォールバック (`getElmVal`)**:
  * ユーザーのUI選択状態（`modeMap`）および重複測定元素（`optElms`）に基づき、利用する計測モード（`ob` または `md`）を決定する。
  * 両方に含まれる（UIでObsidianが選択されている）場合のみ `ob` を採用し、それ以外（チェックが外れている、またはMudrock固有の元素）はすべて自動的に `md` にフォールバックする。
* **LOD（検出限界）の置換処理**:
  * 現状、`< LOD` と記録された値は、計算時に「抽出した当該元素のデータ群の中での最小値」に置換される。
  * ※将来的に、機器固有のLOD値が判明次第、GLB定義に基づく固定値置換に改修される予定である。
* **検量線の保存 (`検量線` シート)**:
  * 算出された補正モデル（スロープと切片）は、別の機会や後段の処理で再利用できるよう、任意の名前をつけて `検量線` シート（`GLB.appShts.crct`）に保存される。
* **最終データの標準化出力 (`PXRF` シート)**:
  * 指定したモードマップに基づいて、複数モードの列を1つの元素列に統合（標準化）し、`PXRF` シートに出力する（`ENTAct.pushStdz`）。
  * **【重要】** ここでは検量線を適用した補正値への再計算は**意図的に行わない**。あくまで生の計測値を出力し、補正の適用およびプレビューは後段の Report 層が担当する。
